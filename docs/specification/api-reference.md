## `list_boards`

`GET /api/boards` · who: anyone (no credentials) · MCP tool `list_boards`, `vb` command `vb list-boards`

## `get_board`

`GET /api/boards/{board}` · who: anyone (no credentials) · MCP tool `get_board`, `vb` command `vb get-board`

Read one board as it is now: the full View (regions, nodes and links, meaning only, no coordinates), the person's answers on every node, each node's latest version, and `head`. On a board agents write to, it also carries the open grant requests (`requests`) and each region's holders (`holders`), both left out when empty. Pass the board id. Use it to see the whole board before you draw on it; use `show_node` for one node's history. `state` and `versions` are keyed by node id, the string form of the node number.

### Inputs

| Name | Where | Type | Required | Description |
|---|---|---|---|---|
| `board` | path | string | yes | The board id, from list_boards. |

### Answer

**200**: The board.

Media type `application/json`.

| Field | Type | Always there | Description |
|---|---|---|---|
| `head` | integer | yes | The ledger's latest `seq`; 0 when it is empty |
| `view` | object | yes | One board as the page draws it: meaning only, no coordinates. A node's id is the string form of its number; `n` is set only on items. |
| `state` | object | yes | What the person has done on this board: each item's status, pins and chosen layout modes. |
| `versions` | object | yes | Each node's latest version number, by node id. |
| `requests` | list of object | no | The grant requests on this board the person has not answered, oldest first; left out when there are none. The person answers one with `grant` or `deny` and its `seq`. |

## `check_responses`

`GET /api/boards/{board}/responses` · who: anyone (no credentials) · MCP tool `check_responses`, `vb` command `vb check-responses`

Read what the person did on a board after a ledger position, including the answers to your grant requests. Pass `after`, the `head` you last saw (0 for everything), and optionally `limit` and `wait` (0-60 seconds) to hold the call until the person presses Send or answers a request. A wait that times out returns `{ responses: [], head }`. A note is reported as the `comment` or `context` act that made it, carrying the note's latest text and kind, again whenever the person edits it; a note removed before you could see it never appears, and a `note-remove` appears only for a note you may already have read. The server keeps no state for you: pass back the `head` you got. `more: true` means read again at once. With your Bearer secret the answer covers only the containers you hold.

### Inputs

| Name | Where | Type | Required | Description |
|---|---|---|---|---|
| `board` | path | string | yes | The board id, from list_boards. |
| `after` | query | integer | no | A ledger `seq`: return what came after it. 0 (the default) means from the start. Pass the `head` you last saw. |
| `limit` | query | integer | no | How many to return at most (default 100, at most 500). |
| `wait` | query | integer | no | Seconds (0-60) to hold the call until the person presses Send or answers a request. 0 answers at once. |

### Answer

**200**: The person's actions.

Media type `application/json`.

| Field | Type | Always there | Description |
|---|---|---|---|
| `responses` | list of object | yes | The person's actions after `after`, oldest first. |
| `head` | integer | yes | The ledger's latest `seq`; 0 when it is empty |
| `more` | `true` | no | Present, and true, only when there is more to read or the answer repeats an earlier one |

## `request_grant`

`POST /api/grants` · who: an agent (Bearer secret from `join`) · MCP tool `request_grant`, `vb` command `vb request-grant`

Ask the person for write access to one container, named by `board` and `region`. Call it once when `write_board` answers `needs-grant`, with a `reason` so the person knows why; then wait for the answer in `check_responses` and resend the same items with the same keys. If you already have an open request for that container it is returned with `replayed: true`; if you already hold the container you get `{ held: true }`.

### Inputs

| Name | Where | Type | Required | Description |
|---|---|---|---|---|
| `board` | body | string | yes | The board that holds the container. |
| `region` | body | string | yes | The container (region) you need to write to. |
| `reason` | body | string | yes | Why you need write access, so the person can decide. |
| `key` | body | string | no | The agent's retry key, scoped to the agent across the project |

Example request:

```json
{
  "board": "pricing",
  "region": "later",
```

## `write_board`

`POST /api/boards/{board}/write` · who: an agent (Bearer secret from `join`) · MCP tool `write_board`, `vb` command `vb write-board`

Write to one board: draw boards, regions, nodes and links, and answer the person with replies, proposals and park bundles. Pass `items` (at most 200), run in order; each item has a `type`: `board`, `region`, `node`, `link`, `unlink`, `reply`, `propose` or `park`. Give each item a `key` so a retry never writes twice, and `base` (the version you read) on a node update so a stale edit fails. It answers 200 with one result per item, plus `head` and `pending` (items waiting for your answer). An item in a container you do not hold fails with `needs-grant`. You cannot decide an item: `propose` acknowledge or drop and the person decides.
