## Next, in this order

### A. The launcher (maintainer asked for a careful, top-level strategy first)

A double-click page to pick a repo folder and launch its board; outside agents find the right
board without hand-set ports. Strategy given to the maintainer (chat, 2026-10-09):

1. A small launcher process on localhost, started by double-clicking a desktop file (a macOS
   `.command` now; an `.app` or an nclite screen later).
2. Its page: recent projects, a folder browser (served by our server; a web page can't return
   real paths), a port picked for you (next free from 4466), Launch / Stop / Open per project.
3. A registry of running boards (folder → port, process) in the user's home
   (`~/.visionboard/boards.json`). Every board server, however started, registers on start and
   removes itself on exit. The per-ledger lock stays.
4. MCP routing: `vb-mcp` started inside a repo looks its own folder up in the registry (unless
   `VB_SERVER` is set), so one MCP entry works for every project; no running board gives a clear
   "start the board for this folder" message.
5. One ledger per folder (`<repo>/.visionboard/`), created on first launch.
6. Safe by default: localhost only, folder browsing limited to the home folder, it starts only our
   own server.

Open questions to settle before a task set: ledgers inside each repo vs one central store; the
launcher always running vs started on demand; what the desktop file is on each computer.

### B. Every node is part of the conversation (maintainer's thinking, 2026-10-09)

The maintainer's view: the board is a threaded conversation in context. The agent explains,
proposes and describes through nodes; most are not questions. The person must be able to respond
to any node: acknowledge ("understood"), drop, comment, ask for more context, save for later (for
themselves). Questions still require answers. Arrows only for real flows; node numbers give the
reading order, so every node needs a number.

Today (code facts): only nodes with `item: true` get a number and action buttons
(`packages/format/src/board-view.ts`, `...(item && { n })`; `packages/ui/src/node/node-core.ts`
`offers`); the agent decides `item`. Each kind offers its own actions (`NODE_TYPES` in
`packages/format/src/node-types.ts`; e.g. a finding can't be dropped). Every node already has a
number in the ledger (D-017); the view hides it on non-items.

Questions to answer in the plan:
- Numbers on every node: a view change, or does `item` go away?
- Which nodes need an answer (stay open, count in "N of M decided", owe the agent) vs carry the
  actions without blocking? (Proposal: questions and decisions need answers; everything else is
  information with the same actions, optional.)
- What each action means on information: acknowledge = understood; drop = not relevant; later =
  the person's own bookmark, and whether the agent then owes a handover (today "later" obliges a
  park bundle, D-020).
- What the counts, conditions rows (`item.owed`, `item.unseen`, `item.new`), `list_open`, Send
  and the skill do with non-question nodes.
- Format change (ledger version), contract first, as usual.
