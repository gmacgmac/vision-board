# N12_FE_01_incremental-board: The board does work in proportion to what changed

> **Parent**: [TASK-STATUS.md](./TASK-STATUS.md) · **Tracker**: N12 · **Spec**:
> `docs/specification/performance.md` (budgets and approach 1-7, binding) · **Rules**: 9, 15 ·
> **Model**: Opus 5.5

## Objective

The board page stops rebuilding and re-measuring everything on every event. An event updates
only the cards it touches, re-lays out only the containers they sit in, redraws only the links
that touch a moved box, and never re-fetches the whole board. Off-screen cards stay cheap. The
budgets in `performance.md` are enforced by tests that COUNT the work, not only time it.

## Known today (facts brief §C6, `controller.ts`)

- `watch` re-runs `openBoard` (a full fetch) 150 ms after any change.
- `build` rebuilds every card and region element; `relayout` updates every card, measures every
  card (`render.ts` `measure`), lays out the whole board and redraws every wire.
- `controller.ts` is 400 lines (over the 300 warning). Split it as part of this task along the
  seams in the brief (agent access, boards/loading, wiring, navigation) so the incremental code
  has its own module; end under 300 if you can, and say why if not.

## Rulings (do not reopen)

1. **Same picture.** For any sequence of events, the incremental result equals a full rebuild of
   the same state: positions, sizes, links, counts. A test drives random event sequences (seeded)
   and compares the two after each step.
2. **Apply events, don't re-fetch.** The live-update stream already carries each change; the page
   folds it into the state it holds through the shared action layer (no second fold). A full
   fetch is only for opening a board, a gap in `seq`, or a format it can't apply; count them.
3. **Layout per container.** `packages/layout` gains a way to lay out one container and repack
   (the pure functions stay pure; caching lives in the page, keyed by container and the inputs it
   depends on). The collision pass from 2d stays per container.
4. **Measure only what changed.** A card is re-measured only when its content, size tier, state
   or notes changed. Reads before writes, one frame per batch (`requestAnimationFrame`).
5. **Off-screen and far.** Cards outside the visible area (plus a margin) get
   `content-visibility: auto` or an equivalent that keeps their size known to layout, their
   keyboard order and their accessible name. No visual change on screen.
6. **Counting hooks.** The page keeps counters (cards updated, measured, containers laid out,
   links redrawn, full fetches) behind a test-only hook that ships nothing extra to users (for
   example read only when a test flag is set). Name it once and document it in performance.md.
7. **Timing tests run alone.** The budget timing tests (including the existing Markdown 50 ms
   test, which flakes under full-suite load) run in their own serial step, so parallel unit tests
   cannot fail them. Keep the numbers in performance.md.

**Unsettled**
1. Links: every route is worked out again each draw (pure, ~1 ms) and only changed connectors are
   written. That is more than "links that touch a moved box" when a moved card shifts the port of
   a neighbour's other link on the same side; needed for the same picture. Approach 2's wording
   could say "only connectors whose route changed".
2. Per batch the page still does O(cards) plain JS (boardView/boardState/boardAccess, `nodeState`
   per card, cache keys, routes); only the DOM work is proportional. Measured inside the 50 ms.
3. Opening reads the whole project ledger at 500 lines a call: 4 calls today, but 200 sequential
   calls on a 100,000-event project. A checkpoint or a larger page for the page's own read would
   fix it; not needed for any budget yet.
4. `boardData` repeats the five-line composition of the server's `getBoard`
   (`apps/board/server/reads.ts`, outside this task's inputs); a test holds them equal. Moving it to
   `packages/actions` and calling it from both removes the duplicate.
5. A line with an unknown `v` triggers a full re-read, which folds it the same way; reloading the
   page (to get a build that knows the format) may be the better answer.
6. No feature flag: the behaviour is meant to be identical (same-picture test), so rule 12 was not
   applied; say if a kill switch is wanted.
7. `firstDrawMs` is taken two frames after the synchronous first draw (after its paint).
